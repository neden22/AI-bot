# Наступний етап: Walt MCP / реальний брокер

Поточний агент **не підключений** до Walt, MCP або будь-якого торгового акаунту. Наявність адреси сервера на скриншоті не визначає схему його інструментів, права, спосіб авторизації чи гарантії виконання. У репозиторії немає вигаданих методів Walt або прихованого live-перемикача.

## Що потрібно до реалізації

1. Офіційна документація Walt MCP, підтримуваний transport і авторизація.
2. Реальний список tools та JSON-схеми для balance, positions, orders, fills, place / cancel.
3. Тестовий акаунт або sandbox, обмеження API, правила комісій, мінімальних сум і precision.
4. Визначені користувачем сума, активи, режим підтвердження, ліміти втрат і правила зупинки.

Не коміть токени, seed-фрази чи приватні ключі. Реальні повноваження мають бути мінімальними; права на виведення коштів торговому процесу не потрібні.

## Архітектура live adapter

- Розділити PaperBroker і LiveBroker; режим має бути видимий у кожній сторінці та звіті, зі своїми БД та конфігурацією.
- Передавати тільки валідовану `OrderIntent` через детермінований risk gate. LLM залишається read-only або може запропонувати intent, який ще потребує валідації.
- Зберігати унікальний client order ID **до** зовнішнього запиту. Після timeout не повторювати розміщення навмання: спочатку отримати стан за цим ID.
- Моделювати accepted, rejected, partially_filled, filled, cancel_pending, cancelled, unknown. Поточні спрощені paper-стани для live недостатні.
- Відновлювати баланс, відкриті ордери та fills із брокера при старті й регулярно робити reconciliation.
- Враховувати tick size, quantity step, min notional, округлення, часткові fills і фактичні fees.
- За підтримки провайдера ставити захисні ордери на його стороні. Локальна перевірка раз на 30 секунд не замінює біржовий захист.
- Додати rate limiting, retry з jitter для безпечних reads, circuit breaker, timeout бюджети та журнал дозволених / відхилених намірів.
- Налаштувати доступ до UI, керування секретами ОС, моніторинг сервісу та сповіщення про збій.

## Критерії готовності

Sandbox-перевірки дублювання запиту, втрати мережі одразу після submit, часткового виконання, restart під час open order, відмови cancel, застарілих даних, збоїв авторизації й відновлення outbox. Після цього — окрема оцінка стратегії на історичних даних із комісіями, slippage, out-of-sample періодом і захистом від look-ahead bias.

Можливі наступні корисні функції: replay / backtesting, мультистратегія з порівнянням результатів, метрики drawdown / expectancy / profit factor, журнал причин кожного сигналу, market-data WebSocket, readonly MCP-сервер ORBIT для звітів та risk telemetry.
